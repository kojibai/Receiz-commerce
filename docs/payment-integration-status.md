# Payment integration status

App integration checked against the installed Receiz SDK 128.0.0 on 2026-10-06. This document does not establish completed live payments.

## Implemented in this patch

- Account permission uses the existing Identity Seal and SDK proof-authority challenge with explicit consent inside the app. The passphrase stays local, exact encrypted source bytes are reverified at the permission boundary, and the non-refreshable transport capability is limited to five minutes. Granted scopes are introspected before installing the HttpOnly cookie. Invalid profile reads no longer report a connected account.
- In-app permission entry binds the intended action: merchant publishing requests record permission, billing requests wallet-read permission, and customer entry remains on the customer account surface. Server failures carry the exact purpose back to the dialog. An arbitrary return URL cannot navigate away from the app.
- Server SDK clients inherit an explicitly configured `RECEIZ_APPLICATION_ID` for native namespace resolution. An explicit SDK application binding is preserved. This is a transport coordinate and never creates proof authority; an OAuth client ID is not silently rewritten to fit another validator.
- The legacy OAuth start URL now returns to an in-app account surface. Checkout and billing errors open the in-app permission dialog. No merchant or customer payment action opens a Receiz website popup.
- Ordinary store purchases can start merchant card checkout without requiring the buyer to open Receiz Connect. Collectible ownership delivery still requires the buyer's connected identity.
- Store payments use the published seller username. Platform upgrade and domain payments use `RECEIZ_PLATFORM_USERNAME=bjklock`, added to the existing Vercel project's production and preview environments.
- Incoming payments use the existing public merchant checkout contract; the receiver does not upload a Proof Vault, provide a signing key, or authorize spending from their wallet. Payer identity is explicit and wallet reads must match that payer's verified account. The normalizer retains receiving-account and proof fields from both flat SDK responses and nested settlement responses.
- Merchant card checkout uses `payments.embeddedCheckout` (`POST /api/payments/embed/checkout`). The delegated Connect checkout route funds the authenticated actor and is unsuitable for paying another merchant.
- The iframe receives its secret through the Receiz `window.name` bootstrap contract. Its URL contains the session ID and merchant, without the client secret.
- A server-signed continuation binds the original merchant, quote, funding amounts, tenant, operation, and connected buyer where applicable. Completion queries the original merchant session rather than creating a second checkout.
- `GET /api/payments/embed/checkout/session` verifies the merchant and returns the settled card amount. A complete-but-unpaid session does not activate a plan or complete an order.
- Pending payment context survives closing the panel and reloading. Checkout and plan submissions have guards against concurrent clicks.
- Paid and pending commerce events have separate IDs. Purchased quantities and fulfillment requirements come from the original quote when the current cart changes.
- The product popover frames the whole image with `object-fit: contain`; long descriptions and proof facts open in a separate native dialog. Portrait, wide, square, and short landscape layouts were checked in Chrome.
- Installing a service worker cannot automatically reload checkout. An update reload requires the user to choose Update.
- Seal import and payment-proof inspection share the styled file picker. The Identity Seal passphrase field appears only after consuming the selected seal requires it, resets on source changes, and receives keyboard focus when opened. Its permission ceremony uses the unchanged registered client ID from this app's challenge route.
- The account payment-proof panel independently opens a complete held SDK recovery for both participants through the installed native edge verifier. It performs no network lookup, planning, submission or new payment. The former manual-head form and fabricated pinned price basis were removed. Verified movement alone does not issue order delivery or account access.
- An unavailable or malformed funded Reserve balance fails before creating a card session. It cannot silently become a zero balance and charge the full amount to a card.
- An already-paid idempotent card creation is independently checked against the original merchant status route. Amount, session, reference and any carried merchant binding are checked before accepting payment.
- Embedded form URLs are limited to the configured HTTPS payment origin and exact embedded route/session. Hosted checkout and secret-bearing fallback URLs are rejected.
- Billing continuation preserves the original operation, price and receiver. Resuming cannot switch to a different plan, domain, merchant or tenant, including when two plans have equal prices. A price or receiving-account configuration change cannot rewrite a payment already started.
- Status-only inspection of the signed original session can continue after the five-minute permission expires. It grants no order or account access; mutation still requires the original buyer's permission. A paid card leg alone never reports a Reserve/card split as fully paid.
- The retained v123 compatibility coordinator guards concurrent submissions before storage yields, preserves exact intent bytes at each idempotency coordinate, and resolves a restored attempt before another submission. Recovery cannot substitute a different canonical intent or proceed without the retained intent.
- The owner selected in-app monthly renewal on 2026-10-06. A hosting quote now carries one fixed calendar month, with renewal available during its final 14 days. The paid-through date, renewal button, original-payment resume, and status check appear inside the admin app. Configured public plan prices come from the existing server settings. The pending service month is shown before card payment.
- Monthly recovery carries encrypted original-session coordinates, bound to the merchant, payer, plan, price, and service period. This envelope is transport metadata, not a payment proof or native entitlement. Every recovery rechecks the original SDK merchant payment session; it never creates another checkout or reads/debits a wallet. Paid recovery remains available beyond the short permission/continuation lifetime. Completion replay cannot add another month or duplicate the invoice. A scheduled early renewal independently rechecks the preceding paid month, and a pending renewal preserves already verified current access.
- Live hosted store purchases require a currently verified paid month; an existing customer payment can finish after that month expires. Publishing a paid hosting plan independently checks its original payment rather than trusting the submitted plan label. The monthly coordinates travel in hosted store state when it is published through the existing SDK publication flow; retaining local coordinates alone does not establish a merchant's native order journal.

## Existing SDK and runtime boundaries

### Local edge execution and remote host qualification

On 2026-10-05, the workspace MCP returned `ready: false` from `receiz_offline_seal_status`. The installed Receiz connector separately returned `ready: true` and an available owner-private v120 subject host. Both execution hosts returned `V124_MCP_APPLICATION_ID_REQUIRED` from `receiz_v124_runtime_qualify`. Signing and subject-host readiness must therefore be distinguished from app-bound execution qualification. The app's Vercel client ID does not configure either MCP host automatically. The existing owner must retain the exact admitted Reserve source in trusted device custody with the matching application/audience binding; neither a website login nor copying an OAuth credential admits that source. Do not create a replacement owner identity, broaden the marketplace execution profile, or reconstruct custody from configuration JSON to hide these failures.

The registered OAuth client ID and edge application namespace belong to different operations. The in-app v123 proof-authority exchange uses the unchanged `RECEIZ_CLIENT_ID`. Local edge plans use the application's explicit namespace, such as `receiz-commerce-kit`, and independently verified source/participant custody. They do not require an OAuth client ID in the edge-plan application field or a qualified remote execution host.

Supplying the `rc_` OAuth ID to the SDK's v124 application-namespace field does fail with `V124_APPLICATION_ID_INVALID`. That rejected composition does not establish that this payment flow requires an SDK update. Do not rewrite the client ID, infer remote authority from an application slug, or treat MCP host qualification as a prerequisite for already verified local edge truth. The proposed SDK patch has been removed. No SDK, MCP, AI-skills package, or Receiz main-repository change was applied or published. The integration remains on the matching published 128.0.0 packages; only this app may change and receive a new deployment.

The app adapter now exposes the installed `client.value.edge` methods directly under `v125.value.edge`. Controlled tests verify that the existing SDK can plan and independently inspect both Reserve participant roles with zero HTTP calls while the OAuth challenge retains the original client ID. These tests do not admit a funded source or commit a financial transition. No new SDK version is required to expose or use these existing methods. Receiz's main repository is outside the scope of this task and must not be modified.

### Funded Reserve spending

The real wallet response nests funded cash at `wallet.valueStates.settledBalanceUsdCents`. The displayed account value also includes other value and must not be debited as funded Reserve.

The legacy delegated transfer requires both a conversation ID and the receiver's account UUID. It does not provide this application's merchant Reserve checkout operation. SDK 128's own one-click checkout tests reject funded-wallet settlement without an explicit execution operation.

Spending from a buyer's Reserve through native edge execution requires that buyer's admitted source proof, exact source and destination heads, a canonical Phi intent and price basis, and each participant's verified capability and sealed transition in SDK custody. The retained remote compatibility path additionally requires its active proof-authority grant and appropriate Reserve scopes. The current checkout supplies none of that custody/execution material. A signed continuation or OAuth token cannot replace it. This requirement must not be presented as requiring `bjklock` to supply a funded Reserve source to receive platform fees.

Consequently, an authenticated buyer with funded Reserve is stopped **before any card payment is created**. This applies to both modern and legacy wallet response shapes and resumed split quotes; the unsupported USD-transfer fallback was removed. Guest buyers and connected buyers without funded Reserve can use merchant card checkout. The requested Reserve-first plus card-delta flow is not complete.

The missing integration must prepare and preserve the exact Reserve execution and receiver authority, reserve the wallet portion before exposing a card delta, resolve uncertain outcomes by the same idempotency key, and admit verified sender/receiver successor proofs after commit. A card-paid/Reserve-conflict outcome requires an explicit recovery or compensation path; it must not become a completed order.

The installed SDK also exposes delegated note minting and public merchant note claims. Their presence does not establish Reserve checkout: the current public request contract provides no explicit Reserve-only funding selector or complete split-recovery contract. The current wallet's note-creation UI requires qualified device custody before issuance and says no value moves if qualification fails. A mint-and-claim sequence must not replace native source admission and atomic payment recovery on the strength of an account-balance read. No note was minted or claimed during this inspection.

### Durable merchant orders and account entitlements

`getServerProofStateStore` currently uses in-memory storage. Checkout event admission therefore does not establish a merchant's durable private order journal across Vercel cold starts. The continuation survives in the buyer's browser, but that is not a server recovery queue.

Paid monthly hosting now derives access from an original SDK session check and fixed service period rather than updating global `mockHosting` plan state. `mockHosting` remains a template/configuration source and still participates in legacy domain actions. The carried monthly envelope is not a native issued account-entitlement proof. Connect record records a time proof; arbitrary application event fields do not constitute durable billing state. The billing connection and plan paths no longer call it as a substitute for an application intent or paid entitlement. The existing webhook recovery path still expects legacy intent records and a service access token that is absent from the Vercel configuration.

Before production release, carry checkout intent, original payment-session coordinates, accepted payment evidence, order successors and plan entitlements in sealed source history. Hold complete exact sources in the established artifact custody contract and independently reopen them for recovery. Source-carried replay must preserve predecessors, sibling branches and unknown namespaces; Memory Crystal source continuity cannot turn unsigned receipt JSON into financial authority. Recover merchant orders and paid access from this admitted history when the buyer closes the browser or the server restarts. The public storefront now omits private orders and customers unless the requesting owner has scoped permission. No external database or new dependency is required or added.

### Fulfillment and recurring billing
