# In-app digital delivery

Digital products require a complete native Receiz Record → Seal artifact, owned by the merchant's verified Receiz identity. The upload route reopens the source with the installed SDK, checks the exact enclosing and payload digests and owner, and refuses raw content, legacy carriers and fabricated proof metadata. It does not create a new seal or transfer ownership.

The existing store proof-state transport carries an encrypted SDK material capsule containing the complete original file. AES-GCM binds that transport to its merchant and product; original order coordinates independently bind payment and delivery to the storefront tenant. Merchant uploads work from the platform admin before publishing a subdomain, and a domain change does not reinterpret the source's owner. This envelope and its metadata are weaker transport, never proof authority. No new database, provider, package or SDK change is introduced. The merchant retains the original source. Keep the existing OAuth-state secret stable: changing it invalidates this app's encrypted transport and existing order recovery coordinates.

Before creating a digital payment, checkout verifies every complete source and bounds the entire frozen recovery quote. Supported uploads are at most 256 KiB each; an order recovery token is bounded to 1.5 million characters. Larger files or carts are rejected before payment, never truncated. The original quote freezes the delivery source, so catalog changes do not substitute a different purchase.

The account page downloads purchased proofs in app. The server first checks the original merchant SDK checkout session, including price, reference, receiver and paid status. Identified purchases require the same buyer or receiving merchant; guest purchases use the private unguessable recovery file. Refunds and unpaid sessions do not release files. Every delivery decrypts the retained capsule and independently reopens its complete exact artifact through the SDK. The browser checks its enclosing digest, reopens it again and uses `artifacts.download` on the SDK-issued native artifact. No unsealed payload fallback is offered.

Saving an order recovery JSON file preserves original-session coordinates; that file is explicitly not an enclosing order proof, paid license, native financial recovery or Memory Crystal. A payment receipt is not a sealed order or ownership grant. Status checks and downloads do not create charges, wallet debits, redirects, emails or new authority. Physical fulfillment, access entitlements and native merchant order journals retain their separate source and authority requirements.
