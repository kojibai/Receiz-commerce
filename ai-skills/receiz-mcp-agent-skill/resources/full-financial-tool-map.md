# Full MCP Financial Tool Map

The full MCP library supports financial workflows. Only the reviewed ChatGPT Marketplace plugin profile is restricted to nonfinancial operations. These current adapters call the existing SDK and preserve its operation admission; transport, confirmation, and file locators never become proof authority.

Use the exact registered OIDC client ID as `RECEIZ_APPLICATION_ID`, with the actual application-bound bearer and operation scopes. Keep client secrets, identity keys, and payment/note credentials in the trusted application. The [native session example](../../receiz-proof-authority/examples/registered-native-session.md) covers device-held consent, the proof grant, source publication, and session prerequisites for native execution.

| Tool | SDK path and MCP arguments | Operation boundary |
|---|---|---|
| `receiz_connect_wallet` | `client.connect.wallet()`; `{}` | Requires `receiz:wallet.read`; projects the current authenticated wallet observation. It does not execute Settlement or Reserve. |
| `receiz_connect_transfer` | `client.connect.transfer(body, options)`; `{ body, options?, confirmation? }` | Requires `receiz:wallet.transfer`. `body` carries `recipientUserId`, `unit: "usd" \| "phi"`, and the corresponding decimal amount. Retain the exact `clientNonce` or `options.idempotencyKey` for recovery. |
| `receiz_connect_checkout` | `client.connect.checkout(body)`; `{ body, confirmation? }` | Requires `receiz:payments.create`; `body.amountUsd` is a decimal string. Creates a hosted/embedded card session; session creation does not prove completed payment, funding, purchase, or custody. |
| `receiz_connect_checkout_session` | `client.connect.checkoutSession(query)`; `{ query }` | Requires `receiz:payments.read`; query allows only `checkoutSessionId` or `sessionId`. Provider status and receipt identity remain observations beneath accepted proof. |
| `receiz_payments_embedded_checkout` | `client.payments.embeddedCheckout(body)`; `{ body, confirmation? }` | Public merchant route with `body.username` and decimal-string `body.amountUsd`; existing merchant/provider admission applies. No artificial delegated grant is required. Card session creation is not completed payment or Settlement. |
| `receiz_connect_note_download` | `client.connect.downloadNote(noteId)`; `{ noteId }` | Requires `receiz:notes.read`. Verifies the exact downloaded PNG with public `verifyReceizOfflineSealedFile` from `@receiz/sdk/offline`, requiring `ok`, `integrity.ok`, PNG kind, and unchanged exact SHA-256. Saves the complete enclosing sealed note privately with a digest-bound `artifactReference`. This delivery path accepts the wallet note’s existing enclosing seal and does not issue, claim, or perform native Record/ownership admission. |
| `receiz_bearer_artifact_claim` | `client.artifacts.verifyAndOpen(file)`, then `client.ownership.claimBearerAsset({ artifact: opened.sealedArtifact })`; `{ artifactReference, confirmation? }` | Delegated runtime plus the existing canonical ownership admission. Uses a selected `receiz:file:<sha256>:<name>` workspace source; verifies the complete enclosing artifact and holds its SDK-issued object. Returns the complete verified sealed successor privately. |

Transfer, card-session creation, and canonical bearer claim first return a preview containing a `confirmationDigest` with zero writes. After actual approval, repeat the exact arguments plus `confirmation: confirmationDigest`. Confirmation is single-use and consumed before SDK dispatch, including failed or unknown outcomes; it does not replace proof, scopes, ownership, or payment approval. Note download saves the verified existing artifact privately without issue or ownership mutation. Resolve an unknown result by its existing idempotency/recovery coordinate before a new attempt.

Hosted checkout URLs are public flow coordinates. Checkout `clientSecret` returned by `receiz_connect_checkout`, `receiz_payments_embedded_checkout`, `receiz_connect_checkout_session`, and `receiz_commerce_one_click_checkout` (including nested `checkoutSession.clientSecret`) stays in private host `_meta["receiz/financialCredentials"]` for the trusted UI; it is excluded from model-visible content. Projection covers those actual credential paths and preserves unrelated `proofBundle` and `proofObject` payload fields. Never print that credential or treat it as payment proof.

For canonical bearer claim, the preview verifies the selected complete source and retains the SDK-issued sealed object in the same runtime. Confirmation cannot reconstruct that custody from JSON or detached proof. Execution re-verifies the returned artifact's digest, payload digest, owner, and claim continuity before retaining exact claimed bytes privately. Raw binary, identity proof, and SDK custody handles do not enter model output. Historical V120 instrument claims and retired bearer-claim aliases remain separate protocols.

`client.connect.mintNote(...)` is a disabled legacy issue route: after scope admission it returns `wallet_note_receiving_seal_required`. There is no current MCP mint adapter for that path. Receiver-bound portable `wallet_note` issue requires the existing receiving Custody Seal primitive; never reinterpret a method's presence as successful note issue.

The SDK's `connect.claimNote(...)` and `payments.embeddedNoteClaim(...)` retain distinct legacy wallet-note token compatibility. They have no current direct MCP adapter because the packaged SDK does not expose an enclosing-note-bound verified token projector. Do not lift a regex/text token extractor or raw token into new proof authority. Use canonical bearer-artifact claim or the existing receiver-bound/V125 edge rails with their actual stronger proof prerequisites.

For canonical value admission, use `receiz_v123_value_execute_settlement`, `receiz_v123_value_execute_reserve`, and `receiz_v123_value_execution_by_idempotency`, or the complete [V125 edge lifecycle](v125-economy-tool-map.md). `receiz_commerce_one_click_checkout` returns `wallet_settlement_execution_required` when wallet funds would be applied, with zero wallet application and no card request; it does not supply the separate Settlement execution.

Record a live integration for actual wallet credit, approved payment, seller proceeds, complete bearer delivery, canonical claim, buyer custody, and asset use. Exercise stale custody, concurrent buyers, reload, retries, and lost responses without duplicate funding, payment, delivery, or ownership. Tool inventory, source handlers, configuration, and fixtures prove their own boundaries only; mark every untested deployed stage explicitly.
